# 씨제이씨협동조합 OSMU 워크벤치

씨제이씨협동조합 / 가발 유통 브랜드 **키노피스**를 위한 원소스 멀티유즈(One Source Multi Use) 콘텐츠 엔진.
담당자 메모와 현장 사진 한 벌에서 **네이버 블로그 · 인스타그램 · X · 쇼츠** 4개 채널 콘텐츠를 한 번에 만들고,
각 채널의 실제 레이아웃으로 미리 본 뒤 네이버에 반자동 게시합니다.

기존 `OSMU_admin`(Streamlit + Supabase + 폴링 워커)과 `OSMU_web`(Next.js 워크벤치)을
**하나의 Flet 데스크톱 앱 + 로컬 SQLite**로 통합한 것입니다. (중간 단계였던 Streamlit UI는 제거됐습니다.)

---

## 빠른 시작

```bash
python -m venv .venv
.venv\Scripts\activate             # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
playwright install chromium          # 네이버 게시 자동화용 (선택)

python flet_app/main.py
```

Windows용 .exe는 GitHub Actions(`.github/workflows/flet-windows-build.yml`)가 빌드합니다.

### 자동 배포 (설치 파일 받기)

`main`에 앱 코드(`flet_app/`, `core/`, `ai_workers/`, `installer/`)가 바뀐 커밋을 푸시하면 Actions가 Windows 앱을 빌드하고
설치 프로그램(Inno Setup, `installer/osmu-cjc.iss`)으로 묶어 **GitHub Releases**에 `OSMU-CJC-Setup-v0.1.N.zip`으로 자동 게시합니다.
zip 안에는 `OSMU-CJC-Setup-0.1.N.exe` 하나만 있습니다(카카오톡으로 .exe를 직접 보내면 막히기 때문).
담당자는 아래 주소에서 받아 압축을 풀고 setup.exe를 실행하면 `C:\Program Files\OSMU CJC`에 설치되고
바탕화면·시작 메뉴에 아이콘이 생깁니다. 업데이트도 새 setup.exe를 실행하면 같은 자리에 덮어씁니다.

https://github.com/JaewooLee-AI/OSMU_cjc/releases/latest

코드 변경 없이 다시 빌드하려면 GitHub의 Actions 탭 → `flet-windows-build` → **Run workflow**를 누르세요.
사용자 데이터(DB·API 키)는 `%APPDATA%\OSMU_CJC`에 있어 재설치·업데이트·제거해도 그대로 유지됩니다.
워크플로는 매 빌드마다 러너에서 설치 → 재설치 → 제거를 실제로 돌려, 옛 파일 정리·아이콘·'설치된 앱' 항목·사용자 데이터 보존을 확인합니다.
서명 인증서가 없어 처음 실행할 때 SmartScreen 경고가 뜨면 [추가 정보] → [실행]을 누릅니다.

첫 실행 시 `data/osmu.db`가 만들어지고, `company_info/`에서 정리한 브랜드 킷이 자동으로 채워집니다.
그다음 **⚙️ 설정 → LLM 벤더**에서 API 키를 하나 이상 등록하고 [기본 생성 모델]을 지정하면 바로 사용할 수 있습니다.

`.env`는 전부 선택 사항입니다 (`.env.example` 참고).

## 왜 3-tier를 접었나

원래 구조는 Vercel(Next.js) → Supabase(큐/스토리지) → Streamlit(워커) 3계층이었고,
그 이유는 단 하나 **Vercel 서버리스 함수의 10초 타임아웃**이었습니다.
크롤링 + 비전 분석 + 수천 자 생성은 30초를 훌쩍 넘기니, 프론트는 큐에 INSERT만 하고
별도 워커가 Supabase를 폴링해 처리하고, 프론트는 Realtime으로 결과를 받는 구조였습니다.

한 프로세스로 합치면 우회할 타임아웃 자체가 없어집니다. 그래서 함께 사라진 것들:

| 사라진 것 | 이유 |
|---|---|
| Supabase Postgres | 생산자와 소비자가 같은 프로세스인 큐는 순수 오버헤드. SQLite 파일 하나로 충분 |
| `worker_runner.py` 폴링 루프 | 생성이 앱 프로세스 안 백그라운드 스레드에서 동기 실행됨 |
| Supabase Realtime 구독 | 같은 프로세스라 그냥 리턴값 |
| service_role 키 / RLS 정책 | 브라우저에 노출될 클라이언트가 없음 |
| 30일 TTL cron + Edge Function | 무료 티어 500MB/1GB 한도를 우회하려던 장치. 로컬 디스크엔 한도가 없음 |

## 기능 보완 v2 (대시보드 · 캘린더 · 비용 환산 · 원고 서식)

요청별 가능/조건부/불가 판단과 설계 이유는 [docs/작업계획_기능보완_v2.md](docs/작업계획_기능보완_v2.md)에 있습니다.

- **원고 서식은 본문과 따로 저장합니다.** `campaigns.content`는 평문 그대로이고, 굵게·형광·소제목·인용구·구분선·
  요약 박스·사진 자리는 `campaigns.content_format`(JSON)에 "어느 문장에 무엇을" 식으로 둡니다
  ([ai_workers/formatting.py](ai_workers/formatting.py)). 초안을 쓰는 같은 호출에서 서식 표시를 받아 바로 떼어 내므로,
  검수·SEO·교정·SNS 단계는 평문만 봅니다. 미리보기와 네이버 붙여넣기 때 교정된 본문에 서식을 다시 붙이고,
  자리를 못 찾은 서식은 버립니다.
- **AI 비용**: 모든 LLM 호출의 금액을 호출 시점 단가(`model_prices`, 관리자가 입력)로 계산해 `usage_log.cost_usd`에
  저장합니다. 단가가 없으면 비워 두고 '단가 미등록'으로 셉니다(0원 아님). 생성·수정·서식 적용 중의 호출은
  `repo.usage_scope(글 ID)`로 그 글에 묶여 "이 글 생성 비용"이 됩니다.
- **자동 작성 예약**: [ai_workers/auto_scheduler.py](ai_workers/auto_scheduler.py)가 앱이 켜져 있는 동안 1분마다
  예약 시각이 지난 글을 초안까지 만듭니다. 꺼져 있던 동안 지난 예약은 다음 실행 때 처리합니다. 발행은 하지 않습니다.

## 사진 분석 토큰 최소화

사진 분석은 이 파이프라인에서 토큰을 가장 많이 먹던 지점입니다.
기존에는 **사진 1장당 1회 호출**로, 1024px 이미지와 담당자 메모가 들어간 ~350토큰짜리 지시문을
매번 같이 보냈고, 같은 제품 컷을 열 번 써도 열 번 다시 분석했습니다.

다섯 개 층으로 줄였습니다 (영향이 큰 순서):

**1. 캡션 캐시 (`vision_cache` 테이블)**
사진 *내용*의 sha256으로 캐싱합니다. 같은 컷을 다른 이름으로 다시 올려도 같은 해시라
분석은 평생 한 번, 재사용은 **토큰 0**입니다. 키노피스처럼 제품 스튜디오 컷을 계속 재사용하는
브랜드에서 이게 제일 큽니다.

**2. 메모와 분리된 프롬프트**
기존 프롬프트는 "이 사진을 설명하고, *이 글의 어디에* 넣을지도 판단하라"고 물었습니다.
그래서 캡션이 글마다 달라져 애초에 캐시가 불가능했습니다.
지금은 비전 호출에 "보이는 것"만 묻고, 배치 판단은 어차피 메모·기사·전체 캡션을 다 가진
텍스트 호출이 합니다. 더 싸면서 역할 분담도 더 맞습니다.

**3. 벤더별 최소 과금 해상도**
각 벤더는 이미지를 면적으로 과금하되 하한이 있습니다. `economy` 프리셋은 딱 그 하한까지만 축소합니다.

| 벤더 | 절약(384px) | 균형(768px) | 고화질(1024px) | 축소 없이 3024×4032 |
|---|---:|---:|---:|---:|
| Gemini | **258** | 258 | 1,032 | 6,192 |
| OpenAI (`detail=low`) | **85** | 85 | 85 | 85 |
| Anthropic | **196** | 786 | 1,398 | 16,257 |

**4. 배치 호출** — 미캐시 사진을 최대 6장씩 묶어 한 번에 보냅니다. 지시 프롬프트를 N번이 아니라 1번만 냅니다.

**5. 출력 상한** — 캡션 1장당 40~45토큰으로 `max_output_tokens`를 걸고, 프롬프트에도 글자 수를 명시합니다.

여기에 더해 업로드 시점에 모든 사진을 1280px JPEG로 정규화해 저장하므로(`core/storage.py`),
폰 원본 대비 실제 절감폭은 위 표보다 더 큽니다.

⚙️ 설정 → 사용량 탭에서 **실제 usage 값**(프로바이더 응답에 실려 온 값)과 절감률을 확인할 수 있습니다.
급하면 [이미지 분석 사용] 토글을 꺼서 비전 호출을 0으로 만들 수도 있습니다.

## 컴플라이언스: 의료법·표시광고법

`OSMU_admin`의 가드레일은 **의료법·표시광고법** 기준이었고, 씨제이씨협동조합도 맞춤가발·두피 분야라
같은 기준을 씁니다. 조합은 의료기관·의약품이 아니므로 치료 효능을 약속해서는 안 됩니다.

- 「의료법」 제56조 (의료광고 규제)
- 「표시·광고의 공정화에 관한 법률」

전형적인 위반은 **치료·완치 약속**입니다 —
"탈모 완치", "모발 영구 재생", "병원 치료 대체", "부작용 제로",
보유 인증(KOTITI 등)의 범위를 넘겨 쓰는 표현. 가드레일을 이 기준으로 썼습니다 (`ai_workers/guardrail.py`).
실제 서비스 전 법무 검토를 권장합니다.

2단 방어:

1. **결정론적 치환** — 브랜드 킷의 금기어 사전은 LLM이 무엇을 쓰든 100% 치환됩니다.
   치환어는 **원래 표현과 같은 품사·활용형**으로 골랐습니다. 한국어는 조사가 뒤에 붙어서,
   관형형을 명사구로 바꾸면 "국내 최초로" → "국내에서도 보기 드문**로**" 같은 비문이 나옵니다.
   긴 항목이 짧은 항목보다 먼저 매칭되도록 길이 내림차순으로 처리합니다.

    ```
    입력: 저희 제품은 탈모를 완치하며 부작용이 전혀 없는 최고급 가발입니다.
    출력: 저희 제품은 두피 환경 개선 및 스타일 보완에 도움을 주는 안전성 검증 완료 가발입니다.
    ```

2. **LLM 감사** — 사전에 없는 새로운 과장 표현을 잡아내고, 점수 + 지적 사항 + **표현 단위 교정안**
   (`문제 표현 → 교정 표현`)을 반환합니다. 글 전체를 다시 쓰게 하지 않으므로 응답이 짧아 잘릴 일이 없고,
   지적하지 않은 문장이 몰래 바뀌지도 않습니다. 교정은 코드가 결정론적으로 적용합니다.
   **감사가 실패하면(응답 잘림·형식 오류·API 오류) '통과'가 아니라 '검수 미완료'로 표시**합니다 —
   예전에는 이 경우 100점 통과로 처리되어, 긴 글일수록 검수 없이 나갈 수 있었습니다.
   인스타 캡션과 X 스레드도 각자 브랜드 주장을 하는 별개 텍스트이므로 같은 감사를 거칩니다.
   단 X는 트윗 하나씩이 아니라 **스레드 전체를 한 번에** 감사합니다 —
   감사 시스템 프롬프트가 ~500토큰이라, 5개짜리 스레드를 낱개로 돌리면 300토큰짜리 내용을 보려고
   2,500토큰짜리 지시문을 내는 셈이고, 스레드 맥락 없이 트윗 하나만 본 판단이 더 나을 이유도 없습니다.
   구분자 구조가 깨져 돌아오면 결정론적 치환만 적용하고 원본 스레드를 유지합니다
   (금기어가 살아남지 않는다는 보장은 어느 경로에서든 유지됩니다).

## 브랜드 킷

`company_info/`의 회사 문서에서 뽑아 첫 실행 시 '기본' 킷으로 자동으로 채워집니다 (`core/brand_seed.py`).
빈 칸에서 시작하지 않으므로 **첫 초안부터** 제품명·가격대·인증·화법을 알고 씁니다.

킷은 사업 분야별로 여러 개 둘 수 있습니다(가발 판매·관리 / 창업 교육 / 두피·항암 등, 개수 제한 없음).
새 킷은 '기본' 킷을 복사해서 만들고, 글마다 워크벤치에서 어느 킷으로 쓸지 고릅니다.
킷마다 따로 두는 값은 업종·페르소나·톤앤매너·핵심 팩트·용어집·SEO 키워드·기본 콘텐츠 모드·샘플이고,
블로그·인스타 계정과 금기어 사전·가드레일은 회사 공통입니다(의료법·표시광고법 기준은 회사 전체에 해당).

- 핵심 팩트 15개 (2014년 대한가발협회 주축 설립, ATUM 24개 센서·10분 스캔, 7~10일 배송, KOTITI 수치 등)
- 용어집 14개 (키노피스 / ATUM 3D 두상측정기 / 맞춤가발 / 항암가발 / 가발공장OEM …)

- 페르소나 & 톤앤매너 ("공감 먼저, 해결책은 ATUM·키노피스 팩트로", "치료 약속 금지")

## 네이버 반자동 게시

네이버는 스마트에디터에 봇이 글을 넣는 것을 차단하므로, 의도적으로 **반자동**입니다.

1. [로그인 세션 저장] — Chrome 창이 열리고 직접 로그인하면 세션이 `data/naver_state.json`에 저장됩니다.
   (이 쿠키만은 DB에 넣지 않습니다. 살아 있는 발행 계정 접근 권한이라, 지우기 쉬운 파일 하나로 둡니다.)
2. [지금 게시] — 백그라운드 스레드가 Chrome을 띄워 제목을 입력하고, 본문/사진을 **문서 순서대로 하나씩**
   붙여 넣습니다. 서식은 붙여넣는 HTML에만 담고 에디터 툴바는 누르지 않습니다(인용구 모양 선택 등은 사람이). 마지막 [발행] 버튼은 담당자가 직접 누릅니다. 게시 창은 담당자가 닫을 때까지 열려 있고,
   자동으로 넣지 못한 사진·제목이 있으면 게시 화면에 경고로 표시됩니다. 같은 글을 두 번 누르거나
   여러 글을 동시에 게시해도 클립보드가 섞이지 않도록 붙여넣기 단계는 한 번에 하나씩만 진행됩니다.
3. [발행] 팝업의 태그 입력란은 자동화가 불가능하므로, 생성된 해시태그를 화면에서 복사해 붙여넣습니다.
4. 게시 창이 열려 있는 동안 Chrome 주소가 `blog.naver.com/{아이디}/{글번호}`로 바뀌면(=발행됨) 그 주소를 저장하고
   게시 완료로 바꿉니다. 손으로 게시했다면 [✅ 수동으로 완료] 옆 칸에 주소를 넣습니다.

절대 headless로 돌리지 마세요. 봇 탐지와 최종 발행 클릭 모두 사람이 앞에 있다고 가정합니다.

### 파이프라인 단계 순서

1. 사진 캡션 (캐시·배치)
2. 본문 초안 — 메모 + 기사 + 캡션을 모두 보는 유일한 호출. 서식 표시도 이 호출에서 받고 곧바로 떼어 냅니다
3. 컴플라이언스 가드레일 — 글을 다시 쓰므로 밀도 검사보다 먼저
4. SEO 키워드 밀도 — 2단계에서 *지시만* 한 것을 실제로 검증
5. 금기어 사전 재적용 — 3·4단계는 새 LLM 출력이므로 결정론적 치환을 한 번 더
6. 이미지 태그 백스톱 — 첨부 사진이 조용히 사라지지 않도록
7. 인스타 / X / 쇼츠 / 네이버 태그 — 네 채널을 **병렬로** 생성, best-effort, 실패해도 본문은 살림
8. 서식 정리 — 2단계에서 뗀 서식을 최종 본문에 맞춰 상한을 적용하고, 자리를 못 찾은 것은 버림

2단계 직후 초안을 먼저 저장하므로, 이후 단계에서 API 오류가 나도 비용을 낸 초안은 편집기에 남습니다.
같은 글에 생성·수정이 동시에 두 번 돌지 않도록 막고, 앱이 생성 도중 꺼졌다면 다음 실행 때 '실패'로
표시해 다시 생성할 수 있게 합니다.

## 데이터와 백업

전부 데이터 폴더(설치형은 `%APPDATA%\OSMU_CJC`, 소스 실행은 `data/`) 안에 있습니다: `osmu.db`(SQLite), `assets/`(사진),
`.master_key`(API 키 암호화 키, 0600), `naver_state.json`(네이버 세션), `backups/`(📦 가져오기 직전 DB 사본, 최근 5개).
이 디렉터리만 백업하면 됩니다. PC를 통째로 바꿀 때도 앱을 닫고 이 폴더 전체를 새 PC의 같은 자리에 복사합니다.

### 담당자가 여러 명일 때 — 📦 데이터 옮기기

앱은 PC마다 데이터를 따로 저장합니다. 한 PC에서 세팅한 값을 ⚙️ 설정 → 📦 데이터 옮기기 → [파일로 내보내기]로
`.osmu` 파일 하나에 담고, 다른 담당자 PC에서 [가져오기]하면 같은 상태로 씁니다([core/transfer.py](core/transfer.py)).
OSMU_osw의 같은 기능을 이 앱의 여러 브랜드 킷 구조와 기능 보완 v2 테이블에 맞춰 옮긴 것입니다.

| 항목 | 담는 것 | 가져올 때 |
|---|---|---|
| 브랜드 킷 | 보관하지 않은 킷 전부(`brand_kit`) | **킷 이름으로 맞춤** — 같은 이름은 내용을 바꾸고, 없으면 새로 만듦. 킷 ID는 받는 PC 것을 유지하고, 받는 PC에만 있는 킷은 그대로 |
| 회사 공통·앱 설정 | `company_profile`, `app_settings`, `app_state.naver_format_mode` | 바꿈. 단 받는 PC에 키가 없는 벤더로 모델 선택을 바꾸지는 않음 |
| API 키 | `llm_settings`, `naver_api_settings`, `searchad_settings` | 비밀번호(PBKDF2-SHA256 → AES-256-GCM)로 풀어 받는 PC의 마스터 키로 다시 암호화. 틀린 비밀번호면 아무것도 바꾸지 않음 |
| AI 비용 설정 | `model_prices`, `app_state.usd_krw`·`usage_budget` | 같은 모델 단가는 바꾸고, 받는 PC의 '단가 미등록' 기록을 그 단가로 채움 |
| 키워드 측정값 | `keyword_cache` | 받는 PC에 더 최근 값이 있으면 유지 |
| 제목 이력 | `title_history`(글 ID 태그는 뺌) | 이미 있는 제목은 건너뜀 |

옮기지 않는 것: `campaigns`(글·서식·캘린더 일정·게시 기록), `assets`와 `assets/` 폴더(사진), `vision_cache`, `topics`,
`schedule_rules`(받는 PC의 글·킷 ID에 연결됨), `usage_log`, `naver_api_calls`, 그 밖의 `app_state`(키워드 화면 진행 상태
`sweep:{킷 ID}`, 글자 크기 등), `naver_state.json`(네이버 로그인은 PC마다), `.master_key`(절대 옮기지 않음).
가져오기는 한 트랜잭션이고, 바꾸기 직전에 받는 PC의 DB를 `backups/`에 복사합니다. 다른 회사용 OSMU 앱(OSMU_osw 등)이
만든 파일은 형식 이름이 달라 받지 않습니다.

`data/`를 클라우드에 동기화한다면 마스터 키는 밖으로 빼세요 (앱은 시작할 때 프로젝트 루트의 `.env`를 읽습니다.
마스터 키를 찾지 못했는데 이미 암호화된 키가 저장돼 있으면, 새 키를 만들어 기존 키를 못 쓰게 만드는 대신 오류를 냅니다):

```bash
python -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())"
# → .env 의 ENCRYPTION_MASTER_KEY_BASE64 에 넣고 data/.master_key 삭제
```

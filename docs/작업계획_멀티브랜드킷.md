## 진행 규칙

- **작업 브랜치에서만 작업합니다** (예: `feature/multi-brand-kit`). `main`에 push하면
  `.github/workflows/flet-windows-build.yml`이 **고객용 GitHub Release를 자동 게시**합니다.
  브랜치 push는 exe 빌드(Actions artifact)만 하고 Release는 만들지 않으므로, 확인용 exe는 브랜치 빌드에서 받습니다.
- 작업 단위마다 따로 커밋합니다.
- 실제 LLM 호출이나 Windows 전용 동작(클립보드, 네이버 게시 자동화)이 필요한 검증은 클라우드에서 하지 않고,
  맨 아래 **"로컬 검증 필요"** 목록에 남깁니다. 그 검증은 실제 데이터 복사본이 있는 Windows PC에서 합니다.
- 빌드 주의: `flet_app/pyproject.toml`의 `jni_flutter = "1.0.3"` 고정을 유지합니다. 1.0.4 이상은 flet 1.0.2
  템플릿(jni 1.0.0)과 맞지 않아 Dart 컴파일이 "Constant evaluation error"로 깨집니다.
  flet을 jni 1.1을 쓰는 버전으로 올릴 때만 이 고정을 같이 풉니다.
  같은 이유로 `shared_preferences_android = "2.4.28"`도 고정했습니다(2026-10-17, 2.5.0부터 jni ^1.1 — 작업 3 빌드에서 발견).

## 결정 사항

1. **이 프로젝트는 씨제이씨협동조합 전용입니다.** 다른 회사 온보딩(clone해서 자기 브랜드로 바꾸는 템플릿 용도)은 지원하지 않습니다.
   같은 엔진을 쓰는 다른 저장소와 구조를 맞출 필요는 없습니다.
2. **브랜드 킷을 여러 개 쓰는 구조로 바꿉니다.** 사업 분야별로 킷을 만들고, 글마다 어느 킷으로 쓸지 사람이 고릅니다.
3. **네이버 에디터 세부 서식(인용구·구분선·스티커·글꼴·정렬 등)은 자동화하지 않습니다.**
   자동화는 제목·본문·사진 입력까지만 유지합니다. 네이버 화면이 바뀌면 깨지는 지점이 늘고,
   자동 클릭이 많을수록 블로그 계정이 봇 탐지에 걸릴 위험이 커지며, 꾸미기는 편집 판단이라 사람이 하는 편이 낫습니다.
   (2026-10-23 기능 보완 v2: 서식은 **붙여넣는 HTML에만** 담는 방식으로 넣었고, 툴바 자동 클릭은 여전히 하지 않습니다 —
   [작업계획_기능보완_v2.md](작업계획_기능보완_v2.md) 요청 4.)

## 작업 2 — 멀티 브랜드 킷

### 현재 구조
- `brand_kit` 테이블은 **한 줄로 고정**되어 있습니다: `core/db.py:72` `id integer primary key check (id = 1)`.
- `repo.get_brand_kit()` 호출이 13개 파일, 30군데에 있습니다:
  `ai_workers/content_writer.py`, `keyword_curator.py`, `multi_llm_router.py`, `naver_paste_worker.py`, `vision.py`,
  `core/brand_seed.py`, `core/repo.py`, `flet_app/main.py`, `flet_app/views/` 의 브랜드 킷·네이버 게시·뉴스 큐레이션·설정·워크벤치 화면.
- 브랜드 킷 테이블 안에 **앱 전역 설정이 섞여 있습니다**:
  `default_generation_vendor`, `vision_vendor`, `vision_quality`, `vision_enabled`, `enabled_channels`.
- 키워드 화면(⚙️ 설정 → 네이버 API)의 진행 상태가 `app_state`의 `"sweep"`(🔑 SEO 키워드 새로 고르기 1~4단계)과
  `"category_sweep"`(사업 분야 추가)에 하나씩만 저장됩니다.
- `title_history`(제목 중복 방지)는 글을 지워도 남도록 FK를 일부러 끊어 둔 테이블입니다(`core/db.py` 주석). 아래 삭제 정책이 같은 원리입니다.

### 설계 (착수 시 확정)

**DB**
- [x] 브랜드 킷을 여러 행으로: `name`, `is_archived`(보관 = 숨김 삭제), `sort_order` 정도 추가.
      → `brand_kit`을 `id autoincrement`로 다시 만듦. 킷 이름은 비울 수 없고, 삭제되지 않은 킷끼리 겹칠 수 없음.
- [x] `campaigns`에 `brand_kit_id`와 `brand_kit_name`(생성 당시 킷 이름 스냅샷) 추가. 스냅샷은 글을 만들 때·킷을 바꿀 때·초안을 생성할 때 갱신.
- [x] 앱 전역 설정 5개를 브랜드 킷에서 분리 (별도 설정 테이블 또는 `app_state`).
      → `app_settings` 테이블(한 줄). 회사 공통 값은 `company_profile` 테이블(한 줄)로 따로 분리.
- [x] 키워드 화면 진행 상태(`sweep`, `category_sweep`)를 킷별로. → `sweep:{킷 ID}`, `category_sweep:{킷 ID}`.
- [x] 마이그레이션: 기존 한 줄 → 첫 번째 킷("기본" — 이름은 사용자가 바꿀 수 있게), 기존 글은 전부 그 킷으로 연결.
      앱 시작 시 한 번 실행되는 기존 마이그레이션 방식(`core/db.py`)을 따르고, 여러 번 실행돼도 안전하게.
      → `_migrate_single_brand_kit`: 예전 구조(`brand_kit.blacklist_map` 컬럼 존재)일 때만 한 트랜잭션으로 실행, 실패하면 전부 되돌림.
        클라우드에서 예전 스키마로 만든 DB(킷·글 2개·스윕 진행 상태)를 두 번 마이그레이션해 값이 그대로인지 확인함.

**킷별로 두는 항목**: 이름, 페르소나, 톤앤매너, 핵심 팩트, 우수 포스팅 샘플, 용어집,
SEO 키워드·전환 가중치·검색 타깃 제외 키워드(`non_target_keywords`), 기본 콘텐츠 모드.
**업종**도 킷별로 둠(구현 시 결정) — 업종이 키워드 추천(`keyword_curator._brand_context`)과 글의 배경 설명에 들어가므로, 분야별로 달라야 킷을 나눈 효과가 남습니다.

**공통으로 두는 항목** (킷마다 두지 않음):
- 네이버 블로그 아이디·인스타그램 계정 — 계정이 하나.
- 금기어 사전·가드레일 — 의료법·표시광고법 리스크는 회사 전체에 해당. → 사용자 결정: **공통**.
- 기업명·브랜드명·홈페이지.
- 브랜드 컬러.
- `title_history` — 같은 블로그에 올라가므로 킷과 관계없이 공유해야 중복 제목을 막음.
- 키워드 측정 캐시(검색량·문서 수) — 공유해야 유료 API 호출이 킷 수만큼 늘지 않음.

## 작업 3 — 설치 프로그램(setup.exe)으로 배포

지금은 `flet build windows` 결과 폴더를 zip으로 묶어 Release에 올리고, 사용자가 압축을 풀어 폴더째 실행합니다.
이것을 **설치 프로그램 하나(setup.exe)** 로 바꿉니다. 멀티 브랜드 킷과 독립적인 작업이라
별도 브랜치(예: `feature/installer`)에서 먼저 끝내 따로 배포해도 됩니다.

### 요구 사항
- `C:\Program Files\` 아래에 설치 (64비트 Program Files, 관리자 권한 설치).
- **바탕화면 바로가기**와 시작 메뉴 항목 생성.
- **다시 설치해도 문제가 없어야 함**: 같은 버전 재설치, 새 버전 덮어쓰기, 앱이 켜져 있을 때 설치 모두.
- 제거 프로그램 제공 (Windows "설치된 앱"에서 제거 가능).
- **사용자 데이터는 설치·재설치·제거와 무관하게 보존**: `%APPDATA%\OSMU_CJC`(브랜드 킷, 글, 암호화된 API 키, 네이버 로그인 세션)는 절대 건드리지 않음.

### 구현 방향 (착수 시 확정)
- 도구: **Inno Setup**을 권장 (Program Files 설치·바로가기·업그레이드·제거·한국어 설치 화면을 스크립트 하나로 처리).
  설치 스크립트는 저장소에 둠 (예: `installer/osmu-cjc.iss`).
- [x] **고정 `AppId`(GUID)** — 한 번 정하면 절대 바꾸지 않음. 같은 AppId라야 재설치가 기존 설치를 덮어쓰고 "설치된 앱" 목록에 하나만 남음.
      → `installer/osmu-cjc.iss`의 `{34EEB406-6A85-453A-B114-1F82B055A174}`.
- [x] 설치 경로 `{autopf}\<제품명>`, 64비트 모드(`ArchitecturesInstallIn64BitMode=x64compatible`), `PrivilegesRequired=admin`.
      → `C:\Program Files\OSMU CJC` (경로 길이 제한 때문에 영문 짧은 이름). 관리자 권한이 없으면 `setup.exe /CURRENTUSER`.
- [x] 바로가기: 바탕화면 + 시작 메뉴, 작업 폴더는 설치 폴더.
- [x] **이전 버전 파일 정리**: 덮어쓰기 전에 설치 폴더의 앱 코드·패키지 폴더(빌드 결과의 `app`, `site-packages` 등)를 지우고 새로 깔기
      (`[InstallDelete]`). 그대로 두면 이전 버전의 모듈이 남아 새 코드와 섞일 수 있음.
      → 설치 폴더를 통째로 비우고 새로 깖(`{app}\*`).
- [x] **실행 중인 앱 처리**: 설치·제거 전에 실행 중인 `osmu-cjc-flet.exe`(와 앱이 띄운 Chrome 자동화 창)를 닫도록 안내
      (`CloseApplications` 또는 실행 여부 확인 후 종료 요청). 파일이 잠겨 있으면 덮어쓰기가 실패함.
      → `CloseApplications=force` + `taskkill /F /T` (자식 프로세스인 Playwright 드라이버·자동화 Chrome까지. 사용자가 따로 켠 Chrome은 건드리지 않음).
- [x] 제거 시 `%APPDATA%\OSMU_CJC`는 삭제하지 않음 (`[UninstallDelete]`에 넣지 않기).
      → 워크플로가 설치·재설치·제거 뒤마다 `%APPDATA%\OSMU_CJC`의 표시 파일이 남아 있는지 확인.
- [x] 설치 화면 한국어 (Inno Setup 기본 제공 `Korean.isl`).
      → Korean.isl이 없는 Inno Setup이면 영어로 만들고 빌드 로그에 표시.
- [x] 앱 아이콘: 지금은 아이콘 설정이 없어 기본 Flet 아이콘이 쓰임. 씨제이씨 로고 이미지를 받을 수 있으면 exe·바로가기·설치 프로그램 아이콘으로 지정
      (없으면 사용자에게 요청, 그 전까지는 기본 아이콘).
      → 사용자가 준 로고(182×115)를 투명 배경 512×512로 만들어 `flet_app/assets/icon.png`에 둠. 더 큰 원본을 받으면 이 파일만 바꾸면 됨.
- [x] 버전: Release 태그(`v0.1.x`)를 설치 프로그램 버전으로 전달 (`iscc /DAppVersion=...`).
      → `0.1.{실행 번호}` — Release 태그 `v0.1.{실행 번호}`와 같은 번호.
- [x] 서명: 코드 서명 인증서가 없으므로 setup.exe도 처음 실행 시 SmartScreen 경고("추가 정보 → 실행")가 뜸. 그대로 두고 안내 문서에 적음.
      → 매뉴얼 설치 슬라이드·README·Release 설명에 적음.

### 설치형에서 깨질 수 있는 곳 (확인 후 필요하면 수정)
> 확인 결과 (2026-10-17): flet 1.0.2가 쓰는 serious_python 5.0.0은 Windows에서 앱 코드를 `<exe 폴더>\app`에 둡니다
> (`SeriousPythonWindows.prepareApp`). 그래서 `PROJECT_ROOT`는 `…\app`이고, 거기에는 `data/`가 없어 지금까지의 zip 버전도
> `%APPDATA%\OSMU_CJC`를 써 왔습니다. 그래도 규칙을 "패키징된 앱(`FLET_APP_STORAGE_DATA`가 있음)은 항상 사용자별 폴더"로 바꿔
> 고정했고, 워크플로가 빌드 결과에 `app` 폴더가 있고 `app\data`가 없는지 매번 확인합니다. 설치 폴더에 쓰는 코드는 없습니다
> (DB·사진·키·네이버 세션은 데이터 폴더, 붙여넣기 사진은 임시 폴더, 바이트코드는 `PYTHONDONTWRITEBYTECODE`).
- **데이터 폴더 선택 규칙**: `core/db.py`의 `_default_data_dir`은 "앱 코드 상위 폴더(`PROJECT_ROOT`)에 `data/`가 있으면 그 폴더를 쓴다"입니다.
  빌드 결과물 최상위에는 Flutter용 `data` 폴더가 있으므로, 설치형에서 `PROJECT_ROOT`가 어디로 잡히는지 확인하고,
  **Program Files 안의 폴더가 데이터 폴더로 잡히지 않게** 해야 합니다 (읽기 전용이라 DB 저장이 실패함).
  필요하면 "소스 저장소에서 실행할 때만 `data/`를 쓰고, 패키징된 앱은 항상 `%APPDATA%`"로 규칙을 바꿈.
- 설치 폴더에 쓰기를 시도하는 코드가 없는지 확인 (로그, 임시 파일, 캐시, Playwright 브라우저 경로 등).
  `.env`는 `flet_app/main.py`에서 앱 폴더와 현재 작업 폴더에서 읽기만 함 — 설치형에는 `.env`가 없어도 정상이어야 함.

### 빌드·배포

      (러너에 없으면 Chocolatey로 설치). 브랜치 빌드는 setup.exe를 artifact로, main 빌드는 Release에 첨부.
